1. SYSTEM SUMMARY
-----------------
Stratos is a small server-rendered Flask website for UAE business advisory and
corporate services. Flask handles routing, authentication, session state,
template rendering, and local asset delivery. Jinja templates provide the page
markup. CSS provides the visual system and responsive layout. JavaScript adds
client-side navigation behavior, loading transitions, search, and an appointment
calendar.

The current system is primarily a presentation and prototype portal. It does not
currently contain a database, ORM, email integration, CRM integration, payment
integration, booking API, or external business workflow service.

High-level architecture:

  Browser
     |
     | HTTP GET/POST
     v
  Flask application (app.py)
     |
     +--> Jinja templates (templates/)
     +--> In-memory service content (SERVICE_PAGES)
     +--> In-memory demo users (USERS)
     +--> Signed Flask session cookie
     +--> Local images, logos, and icons
     v
  Rendered HTML + static CSS/JavaScript


2. BACKEND
----------

2.1 Application setup

- Framework: Flask.
- Entry point: app.py.
- Template directory: templates/.
- Static directory: static/.

2.3 Backend responsibilities

Home and content routes render fixed templates. The seven detailed service
routes call service_page(key), which looks up a service in SERVICE_PAGES and
passes the resulting dictionary to service_detail.html. SERVICE_PAGES contains
the page title, description, heading, introduction, sections, FAQs, CTA copy,
and service path.

The service detail template supports these section data shapes:

- paragraphs: a list of text paragraphs.
- items: a list rendered as an unordered list.
- cards: pairs of card heading and description.
- steps: pairs of step heading and description.
- note: an optional note below the section content.

Dictionary access uses explicit get() calls where key names can conflict with
dictionary methods. This prevents Jinja from resolving section.items to the
built-in dict.items method.

2.4 Authentication and authorization

USERS is an in-memory dictionary containing two demo accounts:

- client / stratos2026 / client role.
- admin / stratos2026 / admin role.

On successful login, Flask stores username, role, and display_name in the
session. The login route redirects according to the role. The client and admin
routes independently check session role and redirect unauthorised visitors to
/login.

This is role-based access control at route level, but it is only suitable for a
demo or local prototype. Credentials are hard-coded, there is no user database,
password hashing, account recovery, multi-factor authentication, audit logging,
session timeout, or admin management interface.

2.5 Form handling

The login form is fully processed by Flask. The contact and appointment routes
accept POST in their route declarations, but the current Python handlers always
render the page and do not read or store submitted contact or appointment data.

The general contact forms post back to /contact. A contact submission therefore
has no persistence, success state, email delivery, validation response, or
server-side error handling beyond browser-required fields.

3.3 Visual system

style.css defines the main navy-based palette, typography variables, page layout,
hero treatments, buttons, forms, dashboards, service detail components, footer,
loading screen, responsive breakpoints, and calendar styling. Most pages use
Playfair Display for headings and Raleway for body text through Google Fonts.

Several templates also contain page-specific inline style blocks and inline
styles. appointments.html contains multiple overlapping style definitions for
the appointment layout. This works as a prototype but makes global visual
maintenance more difficult.

3.4 Client-side JavaScript

script.js runs after DOMContentLoaded and has four main responsibilities:

- Hides the loading screen after 500 ms or when the window loads; includes a
  four-second fallback for the page loader.
- Opens/closes the mobile navigation drawer and toggles the services dropdown
  on smaller screens.
- Searches visible section text using prompt() or the mobile search input, then
  scrolls to the first matching section.
- Provides a client-only appointment calendar. It disables past dates and
  weekends, offers weekday and Friday time slots, writes selected values into
  hidden form fields, and displays a confirmation alert on submit.

There are no fetch(), XMLHttpRequest, WebSocket, or AJAX calls. JavaScript does
not send appointment data to Flask or any external service.

- CSS and JavaScript are stored in static/.

4. DATA FLOW
------------

4.1 Public page request

  1. A visitor selects a navigation link or enters a URL.
  2. The browser sends an HTTP GET request to Flask.
  3. Flask matches the URL to a view function.
  4. The view function selects a template and, for service details, selects a
     dictionary from SERVICE_PAGES.
  5. Jinja renders the template, including shared base.html content.
  6. The browser receives HTML and requests CSS, JavaScript, and image assets.
  7. script.js attaches interaction handlers and updates the rendered DOM.

4.2 Service detail data flow

  Browser GET /services/<service>/
       -> service-specific Flask view
       -> service_page(service_key)
       -> SERVICE_PAGES[service_key]
       -> render_template(service_detail.html, page=...)
       -> Jinja loops through page.sections and page.faq
       -> rendered service page

No service content is loaded from a database or API. Changes require editing
SERVICE_PAGES in app.py or the template.

4.3 Login data flow

  Browser submits POST /login
       -> Flask reads username, password, and role from request.form
       -> USERS dictionary lookup and exact password comparison
       -> on success: write username, role, display_name to session
       -> redirect to /client/ or /admin/
       -> protected route checks session role
       -> render dashboard template

  Invalid credentials
       -> no session update
       -> render login.html with error message

The session is stored using Flask's signed cookie mechanism by default. No
server-side user or engagement record is loaded after login.

4.4 Contact form data flow (current behavior)

  Browser submits POST /contact
       -> Flask contact() receives the request
       -> current handler ignores form fields
       -> contact.html is rendered again
       -> no database, email, CRM, confirmation record, or redirect

4.5 Appointment data flow (current behavior)

  Browser selects a date
       -> JavaScript writes booking_date hidden input
  Browser selects a time
       -> JavaScript writes booking_time hidden input
  Browser submits form
       -> handleBooking(event) prevents default browser submission
       -> validates date/time in the DOM
       -> displays a JavaScript alert
       -> appointment is not sent to Flask or stored anywhere


5. USER FLOW
------------

5.1 Public visitor flow

  Home
    -> review positioning and proof points
    -> browse Services, About, Who We Work With, Insights, or FAQ
    -> open a service detail page
    -> read service scope, steps, limitations, and FAQs
    -> select Tell Us About Your Plans
    -> open Contact or Appointments

5.2 Enquiry flow

  Visitor opens Contact or Appointments
    -> reads direct contact details and service context
    -> enters contact/business information
    -> selects preferred contact method and required services where available
    -> submits inquiry
    -> current application re-renders the page without recording the inquiry

Expected production flow would continue with server validation, persistence,
notification, staff assignment, and a user-visible confirmation, but those
steps are not implemented.

5.3 Appointment flow

  Visitor opens Appointments
    -> moves calendar between months
    -> selects a future weekday
    -> selects an available time slot
    -> enters full name, corporate email, and engagement focus
    -> submits appointment request
    -> receives an alert only; no appointment record or confirmation exists

5.4 Client portal flow

  Visitor opens Login
    -> selects Client workspace
    -> enters demo client credentials
    -> Flask creates a client session
    -> redirect to /client/
    -> view hard-coded engagement progress and recent activity
    -> use Message your advisor, Book an appointment, or Sign out
    -> Sign out clears session and redirects to Login

5.5 Admin portal flow

  Visitor opens Login
    -> selects Admin dashboard
    -> enters demo admin credentials
    -> Flask creates an admin session
    -> redirect to /admin/
    -> view hard-coded operational metrics and priority engagements
    -> use Create update or Sign out
    -> Sign out clears session and redirects to Login

Unauthorised direct access to either dashboard redirects to /login. The current
role check prevents the client role from opening the admin dashboard and vice
versa, but it does not provide object-level permissions because no persisted
business objects exist.


6. CURRENT LIMITATIONS AND PRODUCTION RISKS
-------------------------------------------

Functional limitations:

- Contact submissions are not persisted or forwarded.
- Appointment submissions are intentionally intercepted in JavaScript and are
  not persisted or forwarded.
- Dashboard metrics, client activity, and engagement status are static demo
  content rather than live records.
- Article cards point to # and have no article detail routes.
- Cookie Settings is a placeholder link.
- No server-side validation exists for contact or appointment fields.
- No success, failure, or duplicate-submission handling exists.

Security and deployment risks:

- Demo credentials and a development secret key are hard-coded in app.py.
- Passwords are compared as plaintext and are not hashed.
- debug=True should not be enabled in production.
- Forms have no CSRF protection.
- There is no rate limiting, brute-force protection, or login audit trail.
- Uploaded files are not currently supported, so file validation is not an
  active risk in the current flow.
- The custom image route should be reviewed before production deployment to
  confirm that send_from_directory remains constrained to the images folder.
- Privacy and terms pages describe Odoo, analytics, cookies, and data handling
  that are not visibly implemented by this local codebase. Those documents
  should be reconciled with the actual production infrastructure.

Operational risks:

- No requirements.txt, pyproject.toml, or other dependency lock file is present
  in the current workspace inventory.
- No automated test suite is present in the current workspace inventory.
- No deployment configuration, WSGI entrypoint, environment variable setup, or
  database migration system is present.
- Google Fonts and Google Maps require external network access in the browser.

8. CONCLUSION
------------

The current Stratos system is a coherent Flask/Jinja marketing website with a
small role-gated demo portal and useful browser-side interactions. Its strongest
implemented path is server-rendered public content plus session-based demo login.
Its main boundary is that business transactions are not yet connected to a
backend data store: enquiries, appointments, dashboards, and article content
are either ignored, hard-coded, or client-only. A production version should
prioritise persistence, secure authentication, server-side validation, and
operational notifications before relying on the portal for real client work.
